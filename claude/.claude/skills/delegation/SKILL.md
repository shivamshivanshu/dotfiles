# Delegation

How to delegate work and supervise the agents doing it. Pair with [[working-style]].

- Three kinds of worker, kept distinct because they differ in lifetime and cost: a **subagent** is an unnamed Agent spawn — one-shot, reports back, resumable by its agent ID via SendMessage; a **teammate** is any *named* Agent spawn (agent teams are on in settings) — a persistent in-process member that can self-claim from a shared task list ([[agent-team]]), resumable via SendMessage while alive; each idle wakes the lead, so stop it with TaskStop once its work is done; a **Workflow agent** is one step in a deterministic script. A **fan-in agent** is whichever of these merges the others' output. Name the one you mean.
- Keep the main context small, but decide per task whether delegation earns its cost: it buys context preservation and parallelism at the price of spawn latency, briefing effort, and coordination. Delegate when that price pays off — broad searches, bulk file reading, builds/tests whose output needs filtering (otherwise background the run itself, per Verify), audits, research, and sizeable multi-step or separable work go to subagents or background workflows, which return conclusions, not raw output. Do the work inline when briefing it would cost more than doing it — focused edits, quick lookups, and tightly-coupled changes. The main thread is the engineering lead: it takes the user's instruction, plans, chooses the execution shape, and holds synthesis, decisions, focused shared-context edits, and just enough inline scouting to write good briefs. Agents do the work.
- For large, parallelisable work, orchestrate multi-agent Workflows (Workflow tool; the keyword `ultracode` opts a turn in) by intent: [[fan-n]] to average out variance on one question, [[stochastic-consensus]] to explore and debate an open problem, [[agent-team]] to execute a separable implementation plan. Trivial edits and quick lookups stay solo — the fan-out cost is not worth it there.
- Assign each subtask a model tier by complexity: discover the session's tiers from the model options of the subagent-spawning tool (Agent/Task — name varies by harness version) and rank them — never hardcode model names in skills or prompts (agent-definition frontmatter is config and may pin one). The ladder:
  - Janitor/mechanical — run tools, collect output, apply well-specified edits: fastest tier; spawn fast and often.
  - Mid-level — code scraping, summarising code or lower agents' output: middle tiers, effort high.
  - High-level — brainstorming, design, proposing solutions, fan-in/dedup synthesis, final review: strongest tiers.
  - Bias toward the cheaper, faster tiers (currently Haiku- and Sonnet-class) and reach for them often: trivial checks, routine commands, well-specified refactors, and bulk scraping are cheap there and usually good enough — don't default to the strongest tier out of caution.
  - Escalate, don't restart: when a cheap-tier result is unsatisfactory, summarise its findings and hand them up to a strongest-tier agent (Opus-class) to refine and improve, rather than re-running the whole task on the expensive model.
  - When unsure: on a cheap-tier session, omit the override and inherit; on a strong-tier session, name a cheaper tier for anything mechanical — inheriting there is the expensive choice.
  - Wherever a model is named and the surface accepts it (settings, agent frontmatter, `/model`), request the 1M-context variant with the `[1m]` suffix where the model offers one (not Haiku).
- Pick the narrowest agent type that fits, not the catch-all: read-only searching goes to a purpose-built explorer rather than a general-purpose agent with full tool access. The catch-all takes more turns to reach the same answer, and every extra turn re-reads the whole context — agent choice moves cost more than model choice does.
- Balance model *families*, not just tiers: the `codex` agent bridges to the OpenAI CLI, which reads the repo itself and reports back. Its mistakes don't correlate with a Claude agent's, so pair the two whenever the deliverable is an independent read rather than a diff.
  - Send to codex: diff and code review, audits, bug hunts, "did I miss anything", verifying a claim already made, tracing how something works in unfamiliar code, a second opinion on an approach before committing to it. Keep it read-only and let the main thread own every edit.
  - Keep on Claude agents: focused edits, quick lookups, anything needing this conversation's context or house conventions, and tightly-coupled iteration — codex costs minutes of spawn latency and a fully self-contained brief, which swamps the gain on small work.
  - Brief it as a stranger: absolute paths, the exact question, what "done" means, how to verify. It has neither this conversation nor these skills, so inline any constraint that must not be missed.
  - It spends OpenAI quota, not this session's tokens — a codex leg running in parallel is close to free on the token budget. Background it and keep working.
- For non-trivial changes, code review and simplify passes use the review fan-out in [[fan-n]], with at least one codex leg. Cross-family disagreement is signal — chase it rather than averaging it away.
- Before parallelising implementation, build a dependency tree of the changes and delegate by it — mechanics in [[agent-team]]. Trivial, tightly-scoped, or tangled work stays sequential in one context; the tree is for work that is both sizeable and cleanly separable.
- Always review an agent's code before accepting it: read the diff, check it against the plan and these skills, and correct or re-delegate rather than trust it blind. In a [[doc-reviewer]] run its conformance agent reads the diff; the main thread reads its verdict and `git diff --stat`.
- Supervise every spawned agent — they can die silently or stall without reporting. At spawn, guess a cutoff from the task's size (a rough guess, not an estimate worth spending time on) and arm a background `sleep <cutoff>` as the wake-up; one timer per batch, stopped once the batch reports. At the cutoff, check each agent — its output file or its own slice of the tree changed since the last check: progressing → re-arm; stalled → kill. Ceiling 3× the cutoff: kill regardless. After any kill, sweep the repo for half-done changes (`git status`/`git diff`) and clean or finish them, then hand the dead agent's output file to a fresh agent with a sharper brief to continue from — or finish directly if small.
- Give every subagent, teammate and codex leg an output file: pass its absolute path under the day's scratchpad in the brief, have it append each finding or completed step as it goes (an implementer logs steps beside its diff), written for the LLM that reads it next — fan-in or replacement: exact paths, symbols and commands, current state and next step, no narrative — and keep everything outside the file to a one-line reply — path plus count or status. The file is the cutoff's progress signal and what a replacement continues from, so a kill loses no work. Codex writes its `-o` file only at the end, so a dead codex leg is rerun, not continued. Workflow agents are exempt: their output never reaches the main context, and a resumed run reuses finished calls. So are read-only agents (`Explore`, `Plan`): their reply is the output.
- Subagents follow these same skills: name the relevant ones in the brief — as `SKILL.md` paths for agents without the Skill tool — have them run task-level ones (e.g. `simplify`) on their slice, and report results back for the main thread to consolidate. The plan gate binds the main thread; a delegated agent executes its brief and reports ambiguity back.
- Still make focused, shared-context edits yourself rather than delegating them: files already loaded in the main context stay there even when the edit is mechanical; well-specified mechanical edits to files *not* in context go to a fast implementer agent.
